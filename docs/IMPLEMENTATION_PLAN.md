# План реализации

Этапы **1–7 реализованы**. Этапы 8–11 ещё не начаты. [README](../README.md) содержит стек, формулы и параметры; [архитектура](ARCHITECTURE.md) — потоки и владение данными.

## Зафиксированные решения

Один Cargo package, Rust stable, Binance USDⓈ-M + Aster Futures ETHUSDT, snapshot + diff. Книга — предвыделенные `Vec`, публикация всех уровней — triple buffer. Числа — `fixnum` и `Price/Qty/Amount`. Робот читает только опубликованные `book::BookView`, видит `Online/Offline`, выполняет busy polling в отдельном OS-потоке без Tokio. Deadline в цикле контролируют свежесть и периодический вывод.

## Порядок и зависимости

Этапы 1–5 создают проверяемое ядро без сети; 6–8 добавляют протоколы и гейты; 9–11 — запуск, отказы и измерения. Тесты пишутся вместе с компонентами.

## Этап 1. Каркас проекта — готово

- Создать один package: `main.rs` запускает сервис, `lib.rs` экспортирует модули для тестов и benchmarks.
- Зафиксировать toolchain/edition, проверить MSRV и features зависимостей, включая TLS provider.
- Создать `config`, `numeric`, `book`, `md`, `binance`, `aster`, `robot`, `metrics`; добавить CLI help и обработку ошибок запуска.

**Готово:** каркас собирается с `--locked`, запускает help и проходит fmt/Clippy.

## Этап 2. Числа и конфигурация — готово

**Файлы:** `numeric.rs`, `config.rs`.

- Ввести `Fp`, закрытые newtype, checked-конструкторы и операции с сохранением единиц.
- Реализовать ASCII visitor → удаление хвостовых нулей → `from_str_exact`; проверить tick/lot size.
- Описать CLI, проверенные metadata, лимиты и таймауты из README.

**Проверки:** знаки/пробелы/экспонента, лишняя точность, длина строки, границы `i64/i128`, шаг `0.05`, overflow. Потеря точности на входе и в операциях возвращает `PrecisionLoss` с записью в лог, без округлённого результата. Сверка с `rust_decimal` в общем диапазоне.

**Готово:** внешние значения проверяются без `f64`, округления входа и `unwrap/expect`.

## Этап 3. Локальная книга — готово

**Файл:** `book.rs`.

- Создать `Level`, ограниченный diff, bids/asks и scratch. Bids убывают, asks возрастают; количества в книге положительны.
- Реализовать snapshot и merge: вставка/замена/удаление, сохранение неупомянутых уровней.
- Проверять дубликаты, вместимость и crossed book; commit только после проверки обеих сторон.
- Сохранять границы покрытия; потеря достоверного top-5 запрещает `Online`.

**Проверки:** случайные изменения против `BTreeMap`, удаление неизвестной цены, пустая сторона, границы capacity, дальние уровни, ошибка второй стороны без частичного commit.

**Готово:** корректный snapshot + diff без Tokio, роста capacity и обрезки глубины.

## Этап 4. Хранилище и статусы — готово

**Файлы:** `book/publication.rs`, структуры `FeedMetrics` в `metrics.rs`.

- Определить `BookView`: все уровни, покрытие, sequence, `exchange_time`/`platform_time` (Unix ms), `received_at: Option<Instant>`, `Online/Offline`. До применённого diff метки — `None`.
- Создать три независимо предвыделенных слота на биржу; проверить capacity каждого, не полагаясь на клонирование пустого `Vec`.
- Публиковать заполненный слот целиком, включая смену статуса. Все временные метки при смене статуса сохраняются.
- Новая версия книги или статуса доступна роботу через `Output::update()`; отдельного уведомления после `publish()` нет.
- Метрики/epoch/ошибки передавать отдельно через `triple_buffer<FeedMetrics>`; sequence увеличивать при каждой публикации книги.

**Проверки:** медленный читатель, стабильность удерживаемого снимка, целостность уровней/метаданных, переиспользование памяти, пропуск короткого `Offline`.

**Готово:** гейт не ждёт робота; общих блокировок книги нет.

## Этап 5. Алгоритм robot — готово

**Файл:** `robot.rs`.

- Реализовать чистую `evaluate` по двум `BookView`, конфигурации и одному `now`.
- Проверять статусы, timestamps, возраст/skew, покрытие и четыре суммы объёмов top-5.
- Сравнивать относительный mid с порогом через checked `i128`, без деления.
- Возвращать `Hold/LongBias/ShortBias`, статусы и числа обеих книг; отсутствующие значения — `None`.
- Запустить синхронный цикл через `std::thread::spawn`: первый расчёт при старте, далее отдельные `update()` обеих книг без короткого замыкания. Пересчитывать при обновлении, превышении max-age или секундном deadline. На пустой итерации — `spin_loop()`; обработанные deadline исключать до нового состояния. Проверять stop-флаг даже без данных.

**Проверки:** направления, равенство порогу, границы freshness/skew/объёма, `Offline`, отсутствующий timestamp и overflow. Скачок системных часов не меняет возраст/skew по `Instant`; обе временные метки входят в обоснование. Время задаётся тестом.

**Polling:** одновременные публикации двух адаптеров, обновление во время расчёта, `Offline` без нового diff, stale без публикаций и остановка пустого цикла. Проверить, что оба буфера опрашиваются, а `evaluate` не вызывается на каждой пустой итерации. Robot не использует `spawn_blocking`.

**Готово:** все решения воспроизводимы на локальных данных без зависимости от транспорта.

## Этап 6. Протоколы и fixtures — готово

**Файлы:** `binance.rs`, `aster.rs`, `tests/fixtures/`.

- Сверить endpoints/схемы по официальным ссылкам README; сохранить fixtures с происхождением.
- Описать отдельные wire-модели wrapper, diff, snapshot, metadata; проверять символ, событие, ID и числа.
- Нормализовать данные в общие типы, ограничивая размер до неограниченных аллокаций.
- Проверить рынок, единицы и tick/lot size. Из `E` читать `exchange_time`; `platform_time` и монотонный `received_at` фиксировать до парсинга при получении полного WS-сообщения. Проверять формат/диапазон; все метки сохранять через очередь/replay, не заменять биржевое время локальным.

**Готово:** обе модели проходят корректные и повреждённые fixtures без сети, включая превышение лимитов.

## Этап 7. MDAdapter и Binance — готово

**Файлы:** `md/adapter.rs`, `md/sync.rs`, `binance/adapter.rs` и локальные WS/HTTP mocks.

- Определить минимальный `MDAdapter` со статической диспетчеризацией. Запускать корневую future через `block_on` внутри потока гейта.
- Через `select!` обслуживать WS, HTTP, разбор snapshot, таймеры и shutdown. Сохранять HTTP future между итерациями; проверить cancellation safety операций.
- Буферизовать WS во время snapshot. Ограничивать body при чтении chunks; не более одного незавершённого `spawn_blocking` на гейт. Отбрасывать старый `sync_epoch`.
- Реализовать snapshot bridge и sequence checks из README. Replay выполнять порциями с обслуживанием WS; live parse → merge → publish — без `.await` внутри изменения книги.
- Точный повтор игнорировать без освежения данных; остальные ошибки переводят книгу в `Offline` до восстановления.
- Добавить Ping/Pong/flush, watchdog, deadline, HTTP 429 и backoff с jitter.

**Проверки:** границы bridge, gap/регресс/повтор, поздний snapshot, malformed frame, EOF/Close, overflow, таймаут; WS продолжает читаться при медленном HTTP.

**Готово:** mock проходит `Offline → Online → Offline → Online` с правильными timestamps.

## Этап 8. Aster

**Файл:** `aster.rs`, fixtures и integration tests.

- Реализовать `MDAdapter` с Aster endpoints/моделями; переиспользовать книгу, публикацию и общие механизмы `md`.
- Отдельно проверить правила snapshot/diff по документации Aster.
- Повторить recovery-тесты; соединение, очередь, backoff, watchdog и epoch независимы от Binance.

**Готово:** оба гейта выполняют одинаковый внешний контракт; сбой одного не останавливает второй.

## Этап 9. Запуск, supervision и наблюдаемость

**Файлы:** `main.rs`, `config.rs`, `metrics.rs`, runtime-циклы.

- Предвыделить буферы, независимо запустить два гейта и отдельный OS-поток робота с двумя `Offline`.
- В основном потоке обслуживать метрики и завершение всех workers без блокирующего `join()` работающего worker.
- Настроить tracing, lossy writer, `WorkerGuard`; разделить gaps, пропуски публикаций и потери логов.
- Сетевые ошибки восстанавливать локально; panic/неожиданный выход worker и ошибки конфигурации завершать с ненулевым кодом.
- Shutdown гейтов через Tokio `watch`, робота — через `Arc<AtomicBool>` с `Relaxed` (только stop, без публикации данных). Затем `Offline` от гейтов, закрытие с deadline, join всех workers, завершение writer. Учесть уже выполняющийся `spawn_blocking` разбора snapshot, который не отменяется вместе с ожиданием.

**Готово:** одна команда запуска, решения/метрики и штатная остановка во всех фазах.

## Этап 10. Проверки сервиса целиком

**Файлы:** `tests/`, mock-серверы.

| Сценарий | Ожидание |
| --- | --- |
| Обе книги готовы | Решение с числами обеих площадок |
| Медленный snapshot одного гейта | Второй работает; робот выдаёт `Hold` |
| Gap / malformed / disconnect / overflow | `Offline` до восстановления, без скрытой потери diff |
| Успешный replay / старый HTTP-ответ | `Online` / старый ответ отброшен |
| Медленный читатель | Целостная последняя версия, писатель не ждёт |
| Публикация во время расчёта | Робот подхватывает версию на следующем проходе |
| Одновременные публикации и deadline | Проверяются обе книги и свежесть |
| Быстрое восстановление | Краткий `Offline` может быть пропущен, метрики сохраняют сбой |
| Зависший фид / только Ping | `Hold` / watchdog без освежения timestamp |
| Shutdown | Завершение workers и writer без вечного ожидания |

Deadline робота проверять с управляемым временем, таймеры гейтов — средствами Tokio, публикацию — реальными writer/reader потоками. После локальных тестов явно запустить public smoke test: metadata, обе книги `Online`, решения, shutdown.

**Готово:** сценарии проходят; результат сетевой проверки зафиксирован отдельно.

- Проверить capacity и аллокации прикладного пути; транспорт/TLS/ошибки измерять отдельно. Гистограммы предвыделить, выходы за диапазон считать.
- Записать окружение, affinity, lockfile, нагрузку, длительность и выборку. В benchmark сравнить busy polling с вариантом на `Notify` в одинаковых условиях, включая конкуренцию за CPU.
- Обновить команды запуска, примеры решений и ограничения.

**Готово:** воспроизводимый release replay и отчёт с фактическими измерениями.
