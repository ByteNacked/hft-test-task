# Проверки

Triple buffer со счётчиками разрывов: **33 теста**, `cargo fmt --check`, Clippy с `-D warnings` и release-сборка проходят.

Покрытие:

- точный парсинг цен/количеств, диапазоны и шаги инструмента;
- обе схемы сообщений, ошибочные/повторяющиеся поля и лимиты; повторное использование diff-буферов после частичного разбора, сохранение последнего diff и очистка старых уровней;
- snapshot/bridge, непрерывность `pu`, дубли, конфликт и регрессия;
- merge/update/delete, rollback и покрытие; property-сверка с `BTreeMap`;
- публикация до 20 лучших уровней каждой стороны, продвижение глубоких уровней после удаления лучших и восстановление более короткой книги;
- стабильность книги при конкурентном чтении, получение последней версии после серии публикаций, Offline/Hold при быстром восстановлении, запрет Online для старых поколений;
- Long/Short/Hold, порог, возраст, skew, объём и Offline любой книги;
- сквозной путь HTTP/WS → книга → робот: gap, malformed, Close, EOF и oversized для обеих площадок;
- задержанный snapshot, Ping/Pong, overflow, старый HTTP-ответ, HTTP timeout и watchdog при дублях;
- отбрасывание устаревшего parse worker, его ожидание при shutdown, явная ошибка при выходе/panic worker.

Сквозные тесты запускают оба адаптера в общем Tokio runtime с двумя workers. Тесты используют локальные HTTP/WS-серверы и синтетические [fixtures](../tests/fixtures/README.md). Исходы проверяются по книге, решениям и восстановлению соединения; тестовых счётчиков в рабочем коде нет.

## MD → смена bias: рабочая схема потоков

**2026-10-22, Intel Core Ultra 9 285HX, release.** Вместо однопоточного микрозамера используется общий Tokio runtime с **двумя workers**, две независимые задачи фидов, отдельный OS-поток busy-loop робота и штатный поток записи логов. Supervisor работает в вызывающем потоке. INFO-логирование смен bias включено; вывод направлен в файл. Задачи могут мигрировать между workers, закрепления за CPU нет. `max_blocking_threads(2)` совпадает с сервисом, но загрузка snapshot в этот steady-state замер не входит.

Измеряемый путь: отметка получения готового JSON → штатные decode/sequence/merge → публикация лучших 20 уровней → чтение в другом потоке → расчёт и вход в callback со сменой bias. Используются `Runner::apply`, `service::run`, `Robot` и `decision_reporter` из измеряемой версии. Сеть, TLS, сборка WS-сообщения и ожидание запуска задачи **до** отметки получения исключены. Текущая запись лога начинается после конечной отметки; обработка предыдущих логов влияет на последующие решения.

Каждый фид получает 1000 прогревочных и 10 000 измеряемых сообщений с заданной частотой **1000 сообщений/с**. Фиды не ждут робота. Цены чередуются, вызывая реальные LongBiasAster/ShortBiasAster/Hold. В выборку входят только смены bias; отсчёт — от получения более свежего из двух сообщений, книги которых использованы решением. Количество таких выборок не равно количеству публикаций: не каждый апдейт меняет bias, а промежуточные версии могут заменяться.

Сравнение до переиспользования diff-буферов (`7a1768460d2be9825881b0fe45f4d56db5842772`) и после, по одному последовательному запуску в одинаковых условиях. Времена — **мкс**, изменения указаны отдельно для bids/asks. Базовая глубина задана на сторону; перемещаемый best добавляет до одного уровня, поэтому большой сценарий использует 8000, оставляя запас до лимита 8192.

Все сценарии обработали по 10 000 сообщений на фид. Фактическая скорость до и после — около 1000,1 сообщений/с на фид, суммарно 2000,2. Это проверка задержки при заданной нагрузке, **не максимальная пропускная способность**. p99 снизился во всех шести выборках, но p50 на глубине 8000 вырос; общего ускорения во всех режимах замер не доказывает. Максимум после изменения — 517 мкс, до — 1073 мкс. Один запуск без CPU affinity не задаёт верхнюю границу задержки; p99.9 опирается примерно на десять крайних наблюдений.

Повторить на текущем коде и на базовом коммите (последовательно, без параллельных сборок/тестов):

```sh
python3 scripts/validate_hotpath.py --baseline 7a1768460d2be9825881b0fe45f4d56db5842772
python3 scripts/validate_hotpath.py
```

Скрипт копирует код во временный каталог, добавляет туда измерительный harness и запускает release-тест; рабочие исходники не меняет. `--samples N` задаёт число сообщений на фид после прогрева (минимум 5000). В `/tmp/hft-threaded-validation-*` сохраняются `results.json`, `stdout.log` и `events.log`, включая ID потоков в начале/конце работы фидов. Таймеры и массивы результатов подготовлены заранее; наблюдение за задержкой использует атомики без аллокаций. Штатное форматирование и отправка логов остаются частью нагрузки.

## Аллокации и копирования diff

Отдельный предшествующий аудит аллокатора: **0 alloc/realloc/dealloc** на участке JSON → apply → publish → evaluate при книгах 1000/8192 и diff 1/100 уровней на сторону. Это изолированный однопоточный аудит, без сети и логирования; строки удерживались вне измерения. Его результат нельзя переносить на весь многопоточный сервис с логами. Escape-последовательности, неизвестные вложенные поля и ошибки требуют отдельной проверки. В production release-коде устранены пять переносов diff примерно по 128 KiB; merge не менялся.

## Ограничения

Offline публикуется после обнаружения сбоя до ожидания восстановления. Начатый расчёт использует уже приобретённые версии. Offline доставляется через статический счётчик поколения независимо от замены промежуточных публикаций; до приёма новой Online-версии робот обрабатывает Offline. Старые поколения отбрасываются. Робот получает последнюю опубликованную книгу, без накопления очереди и ошибок заполнения. Молчание обнаруживается watchdog, а устаревание — проверкой возраста в роботе. Очередь логов ограничена и при переполнении может отбрасывать записи.
