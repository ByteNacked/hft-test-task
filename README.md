# Binance + Aster order books

Тестовое задание на Rust: два независимых публичных стакана **ETHUSDT perpetual, USDT-margined**, локальное хранение и тествоый сигнал. Только market-data; ордера и приватные API не используются.


## Технические решения

- ETHUSDT perpetual futures на Binance USDⓈ-M и Aster; книги из WS diff + REST snapshot.
- Избегаем использования аллокаций и излишнего копирования данных (интринзик `memcpy`) на hot path.
- Используются отдельные tokio task для сбора маркет даты биржевыми адаптерами. Это по большей части IO bound задача, однако все равно важно чтобы они работали на разных worker'ах и логических CPU.
- lock-free буфер `triple_buffer` для передачи стакана роботу, из минусов излишнее копирование данных, однако такой подход лучше скейлится при маштабировании системы (в противовес подходу с `RwLock` и т.п.)
- Предвыделенные массивы `Qty`, индексируемые ценой, с битовыми картами занятости; роботу публикуются лучшие 20 уровней каждой стороны через triple_buffer.
- Логи пишутся через `tracing` крейт в отдельном потоке.
- Десятичный fixed-point fixnum, типы Price, Qty, Amount.
- Для робота книга имеет только статусы Online / Offline.


## Возможные улучшения вне скоупа тестового задания

- Не использовать busy loop в роботе/стратегии, это не очень хороший паттерн в реальной системе.
- Использовать промежуточный слой представления стаканов для робота (инкрементальное обновление), с выбыром предоставляемой глубины.
- Хорошей практикой является приклепеление каждого worker'а tokio пула к своему физическому CPU с помощью cpu_affitnity.


## Запуск

```sh
cargo run --release --locked
RUST_LOG=info,hft_test_task=debug cargo run --release --locked
cargo test --locked
```

Rust stable, версия зафиксирована в `rust-toolchain.toml`. CLI/ENV:

| Аргумент | ENV | По умолчанию |
| --- | --- | --- |
| `--max-age-ms` | `HFT_MAX_AGE_MS` | 500 |
| `--max-skew-ms` | `HFT_MAX_SKEW_MS` | 250 |
| `--min-depth-qty` | `HFT_MIN_DEPTH_QTY` | 1 ETH на каждую сторону |

## Книга и восстановление

1. Буферизуем WS diff и загружаем snapshot с ID `L`.
2. Отбрасываем `u < L`; первый применяемый diff должен удовлетворять `U <= L <= u`, следующие — `pu == previous_u`.
3. После применения накопленных diff переводим книгу в **Online**. Количества абсолютные, ноль удаляет уровень; точные дубли игнорируются.

Адаптер единолично обновляет предвыделенные массивы `Qty` по индексу `price / tick_size`; битовые карты находят занятые уровни. Кэш top-20 перестраивается только для затронутой стороны и публикуется роботу через triple buffer вместе с актуальными timestamps. Версии двух бирж независимы.

Gap, конфликтующий дубль, регрессия, плохой кадр, overflow или невалидная книга → **Offline → новый snapshot + diff**; при обрыве также reconnect с backoff. Повреждённая книга не откатывается и не допускает diff/Online до восстановления. Второй фид продолжает работать. Проверяются spread и пять уровней каждой стороны в достоверных границах snapshot; потеря покрытия также вызывает resync.

Watchdog: 3 с без применённого diff, Ping и дубли не учитываются. Backoff: база 250 мс–30 с, jitter и `Retry-After`. [Подробнее об архитектуре](docs/ARCHITECTURE.md).

## Сигнал

Робот использует только опубликованные книги. Если одна Offline, данные устарели, skew превышен или объём top-5 недостаточен — `Hold`. Иначе сравнивает mid Aster с mid Binance:

- Aster дешевле более чем на порог → `LongBiasAster`.
- Aster дороже более чем на порог → `ShortBiasAster`.
- В пределах порога, включая равенство → `Hold`.

Гипотеза: Aster догоняет Binance. Прибыльность не проверялась, исполнения нет. Решение сопровождается mid, возрастом и объёмом bid/ask top-5 обеих книг. Сравнение выполняется точно через целочисленные cross-products.

Робот работает в отдельном OS-потоке с busy polling и `spin_loop()`. Пересчитывает при обновлении книги, истечении свежести и сроке секундного отчёта. Это занимает логический CPU; замеры приведены в [проверках](docs/VALIDATION.md). Triple buffer передаёт последнюю опубликованную книгу; промежуточные Online могут заменяться, переполнения нет. Offline передаётся отдельным статическим счётчиком `AtomicU64` для каждого фида: робот сначала обрабатывает Offline, затем принимает только версии после разрыва. Полученная версия стабильна до следующего чтения.

## Числа, время и ограничения

`fixnum::FixedPoint<i64, U9>`, newtype `Price` и `Qty`. Входные числа разбираются за один проход по ASCII прямо в масштабированный `i64`, с проверкой переполнения. Дополнительные дробные нули допустимы; потеря точности логируется как ошибка, без округления. Для сумм и сравнения mid используется `i128`; границы `i64` и число уровней гарантируют вместимость промежуточных результатов.

`exchange_time` — биржевое `E` в Unix ms. `platform_time` — монотонный `Instant` получения полного WS-сообщения до парсинга/очереди; по нему считаются age и skew. Эти метки нельзя вычитать друг из друга: они используют разные часы. Replay сохраняет исходные метки; смена статуса не обновляет их.

| Ограничение | Значение |
| --- | --- |
| Книга, на сторону | 1 048 576 ценовых ячеек (`BOOK_PRICE_SLOTS`) |
| Snapshot / diff, на сторону | 1000 / 4096 уровней |
| Публикация роботу, на сторону | до 20 лучших уровней |
| WS сообщение / snapshot HTTP body | 1 MiB |
| Metadata HTTP body | 8 MiB |
| Sync-очередь | 2048 сообщений и 8 MiB |
| Replay за итерацию | 32 сообщения |

Книга занимает около **16,25 MiB на фид**, включая обе стороны, битовые карты и кэш top-20; два фида — **32,51 MiB**. Максимальная цена — `(BOOK_PRICE_SLOTS - 1) × tick_size`: при шаге 0,01 это 10 485,75 USDT. Выход за диапазон, включая удаление, вызывает ERROR и Offline/resync. Если snapshot или следующие diff снова содержат такую цену, требуется увеличить константу и перезапустить сервис. Полная очистка массивов выполняется только при загрузке snapshot.

Превышение допустимого размера данных или ёмкости sync-очереди вызывает явную ошибку. При восстановлении за один проход применяются до 32 накопленных diff; остальные обрабатываются в следующих проходах без ошибки. На горячем пути нет mutex, блокирующего I/O и покадрового логирования; буферы книги предвыделены. WS/TLS и обработка ошибок могут аллоцировать.

## Логи и стек

`LEVEL:timestamp: событие параметры`, время UTC, stderr. По умолчанию `RUST_LOG=info`:

| Уровень | Содержание |
| --- | --- |
| INFO | Online (синий фон), Offline (красный), смена bias Aster с числами книг (зелёный) |
| WARN/ERROR | Сбой, восстановление или фатальная ошибка; красный фон |
| DEBUG | Подключение/shutdown, `feed state` с последним применённым `u` и `exchange_time` (Unix ms), секундный отчёт робота |

INFO/DEBUG робота и фидов передаются без аллокаций в общую `ArrayQueue`; форматирование и запись выполняются в фоновых потоках. WARN/ERROR на путях ошибок форматируются вызывающим потоком. Обе очереди ограничены 4096 записями и отбрасывают новые при заполнении; потери событий в `ArrayQueue` логируются как ERROR. При штатном выходе очереди дочитываются. Начальные Offline/Hold не логируются как переходы.

Основные библиотеки: `tokio` (один multi-thread runtime, два workers; по task на фид), `tokio-tungstenite` + `rustls` (WS), `reqwest` (REST), `serde`/`serde_json` (типизированный разбор), `arrayvec` (ограниченные уровни), `triple_buffer` (публикация последней книги), `fixnum` (числа), `clap` (CLI), `tracing`/`tracing-subscriber`/`tracing-appender` (логи), `crossbeam-queue` (общая очередь событий логирования), `time` (UTC timestamps логов), `thiserror` (ошибки), `fastrand`/`httpdate` (backoff). `proptest` проверяет книгу и точный парсер. Точные версии — `Cargo.lock`.
